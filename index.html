Foundations

Core terminology

Quick-reference definitions for every SSO and SCIM conversation.

🔐
What is SSO?
FAQ

SSO stands for Single Sign-On — the ability to log into applications using a set of 'master credentials'.

Users log into monday.com with their master credentials. SSO works by transferring the user's identity from one place (the Identity Provider or IdP — think "Okta") to another (monday.com).

📡
What is SAML?
FAQ

SAML is a secure communications protocol used to implement SSO. When a user logs in, the IdP sends a SAML Assertion — basically "I identified this person" — and monday.com uses that to validate and log them in.

"Are you who you say you are? Do you have permission to access what you're attempting to access?"

🔄
What is SCIM?
FAQ

System for Cross-Domain Identity Management — a protocol for user management across multiple applications. Allows easy provisioning (creating), de-provisioning (deactivating), and updating of users.

💡 SSO is not required for SCIM — though using both together is most common for Enterprise orgs.

🏢
What is an Identity Provider (IdP)?
FAQ

An identity provider stores and manages users' digital identities. Internally, think of Okta — that's what our own IT team uses. monday.com only integrates with specific Identity Providers.

⚙️
What is a Service Provider (SP)?
FAQ

A system that provides business services to users. When it comes to SSO, monday.com is the Service Provider.

Example: Customer uses Azure AD as their IdP → Azure is the IdP, monday is the SP.

👥
What is Provisioning?
FAQ

The process of creating, maintaining, updating, and deleting a user's account across multiple applications at once. With SCIM, we can create users directly from Identity Providers like Okta and Azure.

⚡
What level of provisioning does monday.com support?
FAQ
Just-in-Time (JIT)

SSO SAML default. Users are given backend access by IT, but the account isn't created in monday until they log in for the first time.

SCIM Provisioning

IT can create users from the backend before they ever log in. SCIM overrides JIT and makes the IdP (e.g. Okta) the source of truth.

Client phrasing: "Our default method of provisioning is Just-In-Time (JIT) when setting up SSO. This cannot be changed, but it can be overridden by implementing SCIM."

Technical explanations

Detailed breakdowns for technical conversations with IT teams and admins.

Technical SSO vs SAML vs SCIM — what's the difference?
▼
SSO (Single Sign-On)

The general idea of logging in to multiple places in the same way. We log in to monday.monday.com, Vendict, etc. by authenticating with Okta — sign on once, access multiple locations.

SAML

A secure communications protocol used to implement SSO. The IdP sends a SAML assertion — "I identified this person" — and monday.com validates and logs them in. Note: Does not include Google SSO on the Pro Tier.

SCIM

A different protocol for automatically syncing all of an organization's users and groups from the IdP into monday.com. Doesn't require SSO, but is most commonly used alongside it.

Can SCIM be done through multiple IDPs at once?

Generally possible, but not recommended due to potential conflicts:

✕

If a user exists in both IDPs, one will succeed — the other will conflict (SCIM UID is unique per user).

✕

Groups syncing from two IDPs simultaneously can "fight" over users, causing duplication.

NOTE: You can say we can support it if the caveats are explained to the dedicated IT manager.

Technical What type of provisioning does monday.com support?
▼
JIT (Just-In-Time)

Default when setting up SSO. User is given backend access by IT, but the monday.com account isn't created until first SSO login. Restricting access is done via IDP security groups.

SCIM Provisioning

Allows activating/deactivating users directly from the IDP. Also allows provisioning teams and assigning user types by IDP role. Overrides JIT.

⚠️ Note: ADFS does not support SCIM — this is a limitation on their end, not monday's.

Frequently asked questions
QHow can an account control who has access?
▼

By default, a user can sign up for monday.com if the link is shared, taking up a license.

The ideal solution is security (user) groups in the IDP. These groups define who has access — users outside the group will be instructed to contact their administrator.

QCan an account connect to more than one Identity Provider?
▼

Currently no — one monday.com account cannot connect to multiple IDPs (feature in progress). However:

Option 1

One monday → many IDPs: Not currently supported (feature in progress)

Option 2

Many monday accounts → one IDP: Currently possible — IDP creates a separate app connection per monday account.

QHow can admins map over a user type?
▼

User types can be mapped using SCIM provisioning. Depending on the Identity Provider, SCIM can be straightforward for those with IT experience.

See the Technical Deep Dives tab → SCIM attributes section for details on which IDPs support the userType attribute.
